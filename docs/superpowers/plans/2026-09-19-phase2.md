# Phase 2 (v1.1) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver FR-10a (check intervals by value tier, DD-12) and FR-14 (unattended hourly runs on GitHub Actions, DD-9 and DD-13), so the collection prices itself every hour, with or without the author's computer on, and its valuable cards stay fresh.

**Architecture:**
- **Selection moves from SQL to Go.** The store returns every priceable source card as a `card.Candidate`: its rows, whether any row is unpriced, when it was last checked, and its value. A new `internal/priority` package decides which candidates are due, from a tier table, and in what order.
- **Scheduled runs need two small changes in pricewatch:** `--no-wait` (stop instead of pausing when the hour is spent), and a test pinning that a closed database file is complete (SQLite checkpoints its WAL on close), with `Close` errors no longer dropped.
- **Everything else is the workflow's job:** a template in `deploy/github-actions/`, copied into a private data repo that holds the database, the export and the overrides. Overlap, logs and the secret are GitHub features, not pricewatch code.

**Tech Stack:** Go 1.27, standard library, `golang.org/x/time/rate`, `modernc.org/sqlite`. No new dependencies. GitHub Actions for the schedule.

**Spec:** `docs/PRD.md`, in particular DD-9 (the "Concrete shape" section), DD-12 and DD-13. Read all three first.

## Global Constraints

## Decisions this plan implements

**DD-12, four value tiers, never longer than a week.** Chosen 2026-09-19 from the real collection's distribution:

| Value (the card's best row) | Cards | Checked every | Requests a day |
|---|---:|---|---:|
| $100+ | 53 | 1 day | 53 |
| $20 to $100 | 282 | 2 days | 141 |
| $5 to $20 | 593 | 4 days | 148 |
| under $5 | 4,010 | 7 days | 573 |
| **total** | **4,938** | | **about 915** |

That leaves about 85 of the 1,000 daily requests spare, so a missed day takes roughly 11 days to catch up. If that proves too tight, check the $5 to $20 tier every 5 days, which frees about 30 a day.

- **Value:** each row's latest observed market price, falling back to the export price until the row has one. A card's value is the maximum over its rows.
- **Due:** a card with any never-priced row is always due. Otherwise it is due when `now − LastChecked + 1 hour of slack ≥ interval`, where `LastChecked` is the oldest of its rows' latest observations.
- **Order:** never-priced cards first; then by overdue ratio (`elapsed / interval`), highest first; then by value, highest first (DD-8); then by source card ID.
- **Stop early:** a run prices only due cards. Unused budget is simply not spent.

**DD-9 and DD-13, scheduled runs on GitHub Actions:**
- A workflow in the private `pricewatch-data` repo runs `pricewatch run --no-wait --budget 100` hourly at :07, and `import` on demand through `workflow_dispatch`.
- **`--no-wait`:** a spent hour ends the run cleanly, with the unpriced cards deferred. It applies to `run` only. A manual import keeps waiting out spent hours, under a 300-minute job timeout.
- **State:** `pricewatch.db` lives on the data repo's `db` branch as one force-pushed commit. A job restores it, runs, and pushes it back only if every step succeeded.
- **Overlap:** a workflow `concurrency` group, so pricewatch needs no lock. **Logs:** the job log, so pricewatch needs no `--log`.
- **WAL:** SQLite checkpoints the WAL into the main file when the last connection closes, so the job commits `pricewatch.db` alone. A test pins this, and the commands stop dropping `Close` errors.

```go
// internal/card/candidate.go
package card

import "time"

// Candidate is one source card a run might price: every resolved collection
// row it covers, and what due-date scheduling needs to know about it (DD-12).
type Candidate struct {
	SourceCardID string
	Keys         []Mapping
	NeverSeen    bool      // at least one row has never been priced
	LastChecked  time.Time // the oldest of its rows' latest observations; zero if none
	Value        float64   // its most valuable row: latest market price, else export price
}
```

```go
// internal/priority/priority.go
package priority

import (
	"cmp"
	"math"
	"slices"
	"time"

	"github.com/jkhaynes/pricewatch/internal/card"
)

// Tier re-checks cards worth at least Min every Every.
type Tier struct {
	Min   float64
	Every time.Duration
}

// Policy is a tier table, highest Min first, plus slack: a card counts as due
// this much early, so an hourly schedule does not drift later each day.
type Policy struct {
	Tiers []Tier
	Slack time.Duration
}

const day = 24 * time.Hour

// Default is DD-12's schedule: four tiers, nothing waits longer than a week.
// About 915 requests a day for the author's collection.
var Default = Policy{
	Tiers: []Tier{
		{Min: 100, Every: day},
		{Min: 20, Every: 2 * day},
		{Min: 5, Every: 4 * day},
		{Min: 0, Every: 7 * day},
	},
	Slack: time.Hour,
}

// Interval is how often a card of this value is re-checked. A policy with no
// tiers returns 0: everything is always due.
func (p Policy) Interval(value float64) time.Duration {
	for _, t := range p.Tiers {
		if value >= t.Min {
			return t.Every
		}
	}
	if len(p.Tiers) == 0 {
		return 0
	}
	return p.Tiers[len(p.Tiers)-1].Every
}

// Due returns the candidates due at now, most urgent first, at most n of them,
// and how many were due in total. Cards that are not due are left out: a run
// stops early rather than spend budget on them (DD-12).
func Due(cands []card.Candidate, now time.Time, n int, p Policy) ([]card.Candidate, int) {
	type scored struct {
		c       card.Candidate
		overdue float64 // elapsed / interval; +Inf when never priced or no interval
	}
	var due []scored
	for _, c := range cands {
		every := p.Interval(c.Value)
		if c.NeverSeen || every <= 0 {
			due = append(due, scored{c, math.Inf(1)})
			continue
		}
		if elapsed := now.Sub(c.LastChecked); elapsed+p.Slack >= every {
			due = append(due, scored{c, float64(elapsed) / float64(every)})
		}
	}
	slices.SortFunc(due, func(a, b scored) int {
		if o := cmp.Compare(b.overdue, a.overdue); o != 0 {
			return o
		}
		if v := cmp.Compare(b.c.Value, a.c.Value); v != 0 {
			return v
		}
		return cmp.Compare(a.c.SourceCardID, b.c.SourceCardID)
	})
	picked := make([]card.Candidate, 0, min(n, len(due)))
	for _, s := range due[:min(n, len(due))] {
		picked = append(picked, s.c)
	}
	return picked, len(due)
}
```

**Interfaces:**
- Consumes: `card.Candidate`, `card.Mapping`
- Produces: `func (s *SQLite) Candidates(ctx context.Context, source string) ([]card.Candidate, error)`
  - one candidate per resolved source card at `source` whose rows are still in the collection;
  - `Keys` ordered by collection key;
  - `NeverSeen` is true if any row has no observation;
  - `LastChecked` is the oldest of the rows' latest `observed_at`;
  - `Value` is the maximum over rows of (latest market price, else export price, else 0).

`Stalest` goes away; its ordering rules now live in `priority.Due`. The query stays simple, with no CTE to mis-plan: one row per collection key, with its latest observation found through the `(card_id, id DESC)` index. The grouping happens in Go.

> **Go note:** a `LEFT JOIN` that finds no observation yields NULLs. Scanning into `*time.Time` and `*float64` turns those into nil pointers, which is exactly "never priced" and "no market price", with no `sql.Null*` types needed.

```go
// Candidates returns every source card a run might price at source, one per
// source card, with what due-date scheduling needs (DD-12). Choosing among
// them is priority.Due's job, not the database's.
func (s *SQLite) Candidates(ctx context.Context, source string) ([]card.Candidate, error) {
	rows, err := s.db.QueryContext(ctx, `
		SELECT `+mappingCols+`, o.observed_at, o.market_price,
		       (SELECT MAX(c.tcgc_price) FROM collection c WHERE c.collection_key = m.collection_key)
		FROM card_map m
		LEFT JOIN observations o ON o.id = (
		    SELECT MAX(p.id) FROM observations p WHERE p.card_id = m.collection_key)
		WHERE m.source = ? AND m.status = 'resolved'
		  AND EXISTS (SELECT 1 FROM collection c WHERE c.collection_key = m.collection_key)
		ORDER BY m.source_card_id, m.collection_key`, source)
	if err != nil {
		return nil, fmt.Errorf("query candidates: %w", err)
	}
	defer rows.Close()

	var out []card.Candidate
	for rows.Next() {
		var m card.Mapping
		var variant, status string
		var observed *time.Time
		var market, export *float64
		if err := rows.Scan(&m.Key, &m.Source, &m.SourceCardID, &variant, &status, &m.Reason,
			&observed, &market, &export); err != nil {
			return nil, fmt.Errorf("scan candidate: %w", err)
		}
		m.Variant, m.Status = card.Variant(variant), card.Status(status)

		if n := len(out); n == 0 || out[n-1].SourceCardID != m.SourceCardID {
			out = append(out, card.Candidate{SourceCardID: m.SourceCardID})
		}
		c := &out[len(out)-1]
		c.Keys = append(c.Keys, m)

		value := 0.0
		if export != nil {
			value = *export
		}
		if observed == nil {
			c.NeverSeen = true
		} else {
			if c.LastChecked.IsZero() || observed.Before(c.LastChecked) {
				c.LastChecked = *observed
			}
			if market != nil {
				value = *market
			}
		}
		c.Value = max(c.Value, value)
	}
	return out, rows.Err()
}
```

`c := &out[len(out)-1]` takes a pointer to the slice element, so the updates land in the slice itself. It is safe here because nothing appends to `out` while `c` is in use in this iteration.

```go
func (m *memStore) Candidates(ctx context.Context, _ string) ([]card.Candidate, error) {
	var out []card.Candidate
	for _, mp := range m.due {
		if n := len(out); n == 0 || out[n-1].SourceCardID != mp.SourceCardID {
			out = append(out, card.Candidate{SourceCardID: mp.SourceCardID, NeverSeen: true})
		}
		out[len(out)-1].Keys = append(out[len(out)-1].Keys, mp)
	}
```

````markdown
### Value tiers

A run prices only the cards that are due. How often a card is due depends on its value: its
latest market price, or the export price until it has one (PRD DD-12).

| Value | Checked every |
|---|---|
| $100+ | 1 day |
| $20 to $100 | 2 days |
| $5 to $20 | 4 days |
| under $5 | 7 days |

Never-priced cards come first, then the most overdue, then the most valuable. With about
4,900 priceable cards that is roughly 915 requests a day, just under the daily 1,000.

## Scheduled runs on GitHub Actions

pricewatch runs every hour on GitHub Actions, so your computer doesn't need to be on (PRD
DD-13). The workflow lives in a separate **private** repo, because the database and the
export are personal data and this repo is public.

One-time setup:

1. Create a private repo, for example `pricewatch-data`.
2. In its **Settings → Secrets and variables → Actions**, add the secret
   `POKEWALLET_API_KEY`.
3. Add the data and the workflow to its `main` branch:

   ```powershell
   git clone https://github.com/<you>/pricewatch-data.git
   cd pricewatch-data
   Copy-Item ..\pricewatch\data\export.csv, ..\pricewatch\data\expansions.csv .
   New-Item -ItemType Directory -Force .github\workflows
   Copy-Item ..\pricewatch\deploy\github-actions\pricewatch.yml .github\workflows\
   git add .
   git commit -m "collection and workflow"
   git push
   ```

4. Seed the `db` branch with your local database, so nothing is resolved twice. Close any
   pricewatch command or database viewer first, so the file is complete:

   ```powershell
   git switch --orphan db
   Copy-Item ..\pricewatch\pricewatch.db .
   git add -f pricewatch.db
   git commit -m "seed database"
   git push -u origin db
   git switch main
   ```

   If you have no local database, dispatch an **import** instead (step 5).

5. Under **Actions → pricewatch → Run workflow**, choose `run` to check it works. From then on
   it runs hourly at seven minutes past.

After that:
- **Reports** are in each run's log, on the Actions tab.
- **New export:** commit the new `export.csv` to `main` and dispatch an `import`.
- **Looking at the data locally:** download `pricewatch.db` from the `db` branch. The cloud
  copy is the source of truth. A local run against a downloaded copy is not merged back.
- GitHub may delay or skip a scheduled run when it is busy. Progress is durable, so a missed
  hour just means the next run has a little more to do.
````
